\subsection{Extrair}

A Extração é a primeira etapa para obter os dados. Para isso, precisa-se de uma forma de conectar à base de dados e fazer o download dos registros necessários.

Como apresentado na introdução, o Power BI oferece muitos meios de conexão nativos, no caso do TOPdesk, temos uma situação onde um conector atende parcialmente a nossa necessidade, precisando de mais tratamentos para que a rotina seja executada com sucesso. Utiliza-se a função nativa \texttt{Web.Contents}, que permite obter conteúdos de páginas web, configurar cabeçalhos, consultas, chaves de API, tempo de \textit{timeout}, e outros parâmetros retornando uma estrutura contendo a resposta do servidor, o conteúdo recebido e cabeçalhos de resposta \cite{WebContents}.

O TOPdesk retorna os dados da base em páginas com, no máximo, 10.000 linhas, não contemplando toda a base de dados sendo acessada, neste caso, o TOPdesk retornará em seu cabeçalho a resposta 206, e um endereço para o próximo segmento de dados no item \texttt{x-next-page-url}.\cite{TOPdesk_Incident_API} Para reduzir o peso dos parâmetros, utiliza-se o número da página, passado na seção de consulta da URL, para navegar pelos dados. Esse conhecimento resulta na função \texttt{FetchData}, apresentada a seguir:

\begin{lstlisting}
FetchData = (pageNumber as number, pageSize as number, token as text, accumulated as list) =>
    let
        pagePosition = Number.ToText(pageSize * pageNumber),
	    header = [Authorization = Text.Combine({"Basic ", token})],
        source = Web.Contents("https://edf.topdesk.net/tas/api/incidents", [Query = [pageStart=pagePosition, pageSize=Number.ToText(pageSize)], Timeout=#duration(0, 0, 2, 0), Headers=header]),
        json = Json.Document(source),
        status = Value.Metadata(source)[Response.Status],
        result = if status = 206 then @FetchData(pageNumber + 1, pageSize, token, accumulated & {json}) else accumulated & {json}
    in
        result
\end{lstlisting}
\begin{center}
\text{Código da função FetchData}
\end{center}
Esta função recebe como parâmetros o número da página, a quantidade de linhas por página, a string com o token de autenticação e uma lista vazia para armazenar o conteúdo das respostas, executando os seguintes passos em ordem:
\begin{enumerate}
    \item Calcula a posição da linha que inicia a página, para que a resposta desloque-se pelos dados e comece a entrega da linha requisitada, transformando o resultado numa string utilizando a função \texttt{Number.ToText}\cite{NumberToText};
    \item Monta o cabeçalho da requisição, gerando um \textit{registro} \cite{PBI_Tipos} que será passado para a função \texttt{Web.Contents} contendo o valor de "\textit{Authorization}", que indica para a página qual é o tipo de autenticação a ser utilizada e o token para autorizar. Neste caso, usa-se autenticação básica, passando um texto contendo a \textit{string} "\texttt{Basic }" concatenada com a \textit{string} de autenticação, que é formada pela concatenação do usuário e senha, codificados em base 64 \cite{TOPdesk_Login}. Em Script M, a concatenação de textos é feita utilizando a função nativa \texttt{Text.Combine}\cite{TextCombine};
    \item A função \texttt{Web.Contents} é chamada, passando como parâmetros o endereço do \textit{endpoint}\footnote{Segundo a Crowdstrike, um \textit{endpoint} é "...qualquer dispositivo físico que pode ser conectado a uma rede, incluindo computadores, laptops, celulares, tablets e servidores" \cite{Endpoint_Definition}.} da API do TOPdesk, um registro contendo a consulta a ser concatenada na URL, sendo este parâmetro também um registro, contendo os valores \textit{pageStart} e \textit{pageSize} definidos anteriormente na função, o tempo máximo de espera (\textit{timeout}), sendo um parâmetro do tipo duração, e o cabeçalho, sendo este também um registro contendo o valor \textit{Authorization}. Recebe como resposta um texto em formato JSON, o cabeçalho de resposta, com o código HTTP recebido, o conteúdo requisitado, e outros valores não utilizados neste contexto\cite{PBI_Tipos};
    \item A função \texttt{Json.Document} \cite{JsonDocument}, recebe a string em formato JSON obtida no passo anterior, realiza o \textit{parsing}, retornando um registro com as chaves e valores utilizados;
    \item Extrai os metadados associados à resposta de \texttt{Web.Contents}, utilizando a função \texttt{Value.Metadata} \cite{ValueMetadata}, obtendo o conteúdo indexado pela chave \texttt{Response.Status}.
\end{enumerate}

A implementação é recursiva, montando uma lista de listas, que na transformação serão concatenadas. Como Script M é uma linguagem funcional, não possui estrutura de loop como nas linguagens imperativas \cite{Functional_Loop}.

As etapas para a transformação nesta tabela são os seguintes, algumas linhas foram omitidas por serem muito semelhantes:
\begin{enumerate}
	\item Combinam-se as listas obtidas pela função \textit{fetchData} utilizando a função \textit{List.Combine}, que recebe como parâmetro uma lista de listas;
	\item Expande-se a lista resultante pelos registros nela contidos, transformando-os em colunas diretamente tratáveis. A função responsável por isso é a \textit{Table.ExpandRecordColumn}. Ela recebe como parâmetro o nome da coluna que contém os registros, uma lista com quais chaves devem se converter em colunas da tabela, e uma lista com o nome que essas colunas assumirão após a expansão;
	\item Realiza a correção dos nomes de departamentos que possam estar com mais de uma grafia;
	\item Cria uma coluna auxiliar para processamento de texto;
	\item Faz a remoção de texto desnecessário que é resgatado na descrição detalhada do chamado;
	\item Remove a coluna auxiliar;
\end{enumerate}

Após esse processamento, pode-se iniciar o carregamento dos dados clicando no botão "Fechar e Aplicar", a partir desse ponto, o PBI executará as consultas que foram criadas e carregará os dados para o modelo interno da aplicação, permitindo que se monte os visuais.

\subsection{Criação de tabela dinâmica e medida usando DAX}
Para que se possa fazer o acompanhamento de quantos chamados estão abertos por dia, utiliza-se uma tabela dinâmica, que pode ser modificada a depender dos filtros e opções definidos nos visuais. Primeiro. a tabela é iniciada com o intervalo de datas que os dados disponíveis compreendem utilizando o seguinte código:
\begin{lstlisting}
DateTable = 
ADDCOLUMNS (
	CALENDAR ( MIN(chamados[creationDate]), MAX(chamados[completedDate]) ),
	"Year", YEAR([Date]),
	"Month", MONTH([Date]),
	"Day", DAY([Date])
)
\end{lstlisting}
\begin{center}
	\text{Código para inicializar tabela em DAX}
\end{center}

A função \texttt{CALENDAR} toma como parâmetros as datas inicial e final de um intervalo \cite{DAX_CALENDAR}. Já a função ADDCOLUMNS utiliza uma tabela, o nome de uma coluna e uma fórmula para cálculo desta coluna. Essas adições de colunas calculadas são feitas em pares, sempre com o nome precedendo a fórmula \cite{DAX_ADDCOLUMNS}. Ao rodar esta expressão, obtêm-se uma tabela que foi nomeada DateTable. As colunas \textit{Year}, \textit{Month} e \textit{Date} permitem a filtragem por eventos que aconteçam em dias, meses e anos individuais, entregando mais uma opção para o visual.

A seguir, a medida \textit{OpenTickets} é criada, ela calculará a quantidade de chamados que estão abertos em uma data, permitindo a montagem de gráficos de acompanhamento. A listagem abaixo define a medidaL
\begin{lstlisting}
OpenTickets = 
CALCULATE (
		COUNTROWS(chamados),
		FILTER (
			chamados,
			chamados[creationDate] <= MAX(DateTable[Date]) &&
			(ISBLANK(chamados[completedDate]) || chamados[completedDate] >= MAX(DateTable[Date]))
		)
)
\end{lstlisting}
\begin{center}
	\text{Código da medida \textit{OpenTickets}}
\end{center}

A função \texttt{CALCULATE} executará a função \texttt{COUNTROWS} considerando a condicional apresentada na função \texttt{FILTER} \cite{DAX_CALCULATE} \cite{DAX_COUNTROWS} \cite{DAX_FILTER}. Neste caso, serão contadas as linhas que têm chamados com datas de criação anteriores a data que está em \texttt{MAX(DateTable[Date])} e que não tenham data de completude, ou que a data de completude esteja no futuro, obtendo assim a quantidade de chamados abertos no dia.

A montagem do visual deve comunicar ao usuário informações que permitem tomada de decisões estratégicas para o negócio. Portanto, o uso de filtros e de gráficos deve ser escolhido de forma a entregar clareza e não induzir ao erro. Neste relatório, 4 páginas fornecem perspectivas diferentes para que o usuário possa obter informações, auxiliando na tomada de decisões e na detecção de anomalias que possam estar em andamento. O Power BI possui opção nativa para criar histogramas, porém ela não entrega um grau de liberdade adequado na função de divisão de cestas para a aplicação sendo apresentada. Para resolver isso, criam-se duas colunas dinâmicas em DAX, uma fará a contagem de quantos dias um chamado está aberto, a outra classificará os chamados conforme as cestas que foram definidas pela gestão. A decisão de se criar duas colunas separadas permite utilizar o resultado do cálculo de dias em alguma modificação futura.

O primeiro código apresentado faz a contagem dos dias em que um chamado está aberto:

\begin{lstlisting}
totalDurationInDays = IF(ISBLANK(chamados[closedDate]), DATEDIFF(chamados[creationDate], TODAY(),DAY), DATEDIFF(chamados[creationDate], chamados[closedDate], DAY))
\end{lstlisting}
\begin{center}
	\text{Código DAX para o cálculo de quantos dias um chamado está em aberto.}
\end{center}

A primeira função é o \texttt{IF}, que recebe como parâmetros um teste lógico, o resultado do \texttt{IF} caso verdadeiro, e o resultado caso falso, sendo este último opcional \cite{DAX_IF}. A função \texttt{ISBLANK} é o teste lógico, ela recebe uma coluna de uma tabela, retorna verdadeiro caso um campo esteja vazio, e falso caso não \cite{DAX_ISBLANK}. A função \texttt{DATEDIFF} calcula a diferença entre duas datas, recebe como parâmetros a data inicial, a data final, e um identificador para definir a unidade de tempo que será usada para comunicar a diferença \cite{DAX_DATEDIFF}. Um ponto importante a considerar sobre a função \texttt{DATEDIFF} é que ela retorna intervalo negativo caso a data final seja anterior à data inicial, então é necessário se atentar à ordem dos operadores para que os resultados sejam coerentes com o relatório.


O segundo código faz a classificação da duração dos chamados nas cestas definidas pela gestão:

\begin{lstlisting}
	durationBin = IF(chamados[totalDurationInDays] >= 0 && chamados[totalDurationInDays] <= 5, "00 - 05", 
		IF(chamados[totalDurationInDays] > 5 && chamados[totalDurationInDays] <= 10, "06 - 10",
			IF(chamados[totalDurationInDays] > 10 && chamados[totalDurationInDays] <= 20, "11 - 20",
				IF(chamados[totalDurationInDays] > 20 && chamados[totalDurationInDays] <= 30, "21 - 30",
				"30+"
				) 
			)
		)
	)
\end{lstlisting}
\begin{center}
	\text{Código DAX para a classificação das cestas do histograma.}
\end{center}

 Ele cria uma coluna chamada \texttt{durationBin}, que contém os textos informando a qual intervalo cada chamado se encaixa. O código consiste em \texttt{IF}s aninhados que testam o resultado do cálculo da coluna \texttt{totalDurationInDays} e salvam o texto correspondente.
 
 Com essa informação, é possível utilizar o visual de gráfico em barra para montar o histograma, passando para o parâmetro do eixo x a coluna com as cestas, e para o eixo y a coluna com o identificador do chamado, que a visualização utiliza para fazer a contagem.

Nela, os funcionários da TI podem ver a requisição, data de criação, identificador do chamado, e o estado em que se encontra.
